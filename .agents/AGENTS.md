# Workspace Rules - 小工具工坊

本檔是 AI Agent 在本工坊的**運作規則 SSOT**。
工坊管理規範（標籤、命名、README 範本、完工清單）見 [新工具建立流程.md](../docs/00_公共規格/新工具建立流程.md)。

> 本檔中的「使用者」指工坊主人。想讓 AI 用暱稱稱呼你，可以把「使用者」全部取代成你的暱稱。

---

## 0. 適用範圍與優先順序

- 本檔適用於整個工坊與**所有工具**，是唯一的共用規則來源。
- 工具內的文件只記錄該工具**特有**的內容（技術棧、資料結構、專用指令），不得複製或改寫本檔的共用規則。
- 工具需要專屬 AI 規則時，可建立 `NN_工具/.agents/AGENTS.md`，開頭須註明「先讀工坊共用規則」，內容只放該工具特有規則。兩者衝突時以本檔為準。
- 本檔若引用不存在的檔案，視為規則錯誤，應觸發「自我修復」而不是略過。

## 1. 程式品質鐵律

1. **嚴格資源巡查**：主動檢查記憶體 / 控制代碼洩漏、物件過早釋放、執行緒死鎖、檔案鎖定例外。
2. **狀態一致性**：系統真實狀態（電源、螢幕、網路…）必須與畫面上的圖示、通知 100% 同步。
3. **邊界條件**：快速連點、重複啟動、離線、權限不足都必須妥善處理。
4. **可還原**：會修改系統設定的工具必須能完整還原，結束程式時自動還原。
5. **桌面工具標準**：Windows 桌面工具遵循 [小工具設計與互動規範.md](../docs/00_公共規格/小工具設計與互動規範.md)。
6. **拒絕捷徑與幻想**：不為了「先跑起來」而寫違反正確架構的硬塞寫法；只根據實際程式碼現況回答，不假設尚未實作的功能。
7. **先質疑再動手**：接到新需求時，先站在架構師立場提出關鍵問題（真正的使用情境？會動到哪些系統設定？失敗時怎麼還原？會影響哪些現有工具？），確認後再寫程式。

## 2. 建置與提交控制

1. **未經指示不主動編譯**：除非使用者明確說「編譯」、「打包」、「讓我看看」、「測試」，否則不在背景執行 `build.bat`、`npm run build` 等重度編譯。
2. **AI 不擅自 Commit / Push**：除非使用者明確要求，AI 只產出提交訊息，由使用者檢視後手動提交（例如用 GitHub Desktop）。
3. **未說「收工」不主動給提交指引**：開發途中不跳出 Summary / Description 區塊。
4. **雲端同步只在完工後詢問**：開發、測試期間絕不寫入雲端硬碟；發佈標籤為 📤 的工具完工測試通過後，主動詢問：
   > 「這個工具已完工測試通過，請問要同步一份最新版本（執行檔 + README）至雲端硬碟嗎？」
5. **一工具一 repo**：每個工具資料夾是獨立 git repo；工坊 repo 只存規則與文件。只有 🌐 GitHub 工具需要 push。詳見 [新工具建立流程.md](../docs/00_公共規格/新工具建立流程.md) 第 3 節。
6. **工坊整潔**：完成後自動清理編譯過程產生的暫存檔與測試腳本，根目錄只保留 README、規範與 `.agents/`。

## 3. 文件自動同步

### 東西放哪裡（判斷表）
使用者叫 AI「記下來」「存起來」或產生任何需要留下的內容時，**依序**問下面的問題，第一個「是」就是答案：

| # | 問題 | 是 → 放這裡 |
| :-: | :--- | :--- |
| 1 | 還沒做的點子？ | [想法收件匣](../docs/想法收件匣.md)（規則見第 4 節「記想法」） |
| 2 | 正在開發工坊裡的某個工具？ | 該工具的開發日誌 `NN_工具/docs/開發日誌/` |
| 3 | 在改工坊的規則或規範？ | 工坊開發日誌 `docs/03_開發日誌/` |
| 4 | 學新工具、裝環境、搞懂一個概念？ | 學習筆記 `docs/04_學習筆記/`（格式見 [開發日誌規範.md](../docs/03_開發日誌/開發日誌規範.md) 第 4 節） |
| 5 | 工坊以外已經做出來的作品？ | 作品紀錄 `docs/作品紀錄/作品名/` |
| 6 | 金鑰、帳號放在哪？ | [金鑰登記簿](../docs/金鑰登記簿.md)（只記位置，不記金鑰值） |
| 7 | 別人的開源專案，下載來研究或試用？ | 工坊**外面**的 `參考專案/專案名/`（不進工坊 repo；研究心得寫學習筆記） |
| — | **都不是，或拿不準** | **先問使用者，不得自行新增類別**；確認後在本表加一列 |

- 存完一律回報一句「放在第幾格、哪個檔案」，讓使用者能當場糾正。
- 一件事橫跨多格時，寫在最主要的那格，其他格只放連結，不重複寫內容。

### 工具包 ([docs/工具包.md](../docs/工具包.md))
- 安裝、設定或引入新的 SDK / CLI / 套件時，**立即**更新：SDK 放「開發環境與 SDK」，套件放對應工具的「專案相依套件」小節。

### 工具清單 ([README.md](../README.md))
- 新增工具、狀態或發佈標籤變更、啟動方式改變時，同步更新 README 工具清單表格。

### 開發日誌與學習筆記
- 使用者要求寫日誌或「收工」時撰寫，位置與格式嚴格遵循 [開發日誌規範.md](../docs/03_開發日誌/開發日誌規範.md)。

### 公共規範改版
- 修改 `docs/00_公共規格/` 內任何規範時，必須在該檔「📜 變更紀錄」新增一列（版本、日期、變更、需跟進的工具）。

## 4. 快捷指令

### 「開工」
1. **選擇工具**：以互動選單列出工具清單（含「新工具」、「工坊規範」選項），讓使用者點選本次要處理的對象。
2. **前置檢查**：在**該工具的 repo**（或工坊 repo）執行 `git status`。若有未提交變更，先以警示提醒使用者處理（收工或確認可繼續）。
3. **載入脈絡**：讀取該工具的 `README.md` 與最近一篇開發日誌的 Handoff；狀態為 🟠 暫停時，特別說明 README 的暫停紀錄。同時掃描 [想法收件匣](../docs/想法收件匣.md)，列出與本次對象相關的想法（沒有就略過）。
4. **規範版本比對**：比對 README「符合規範」與公共規範最新版本，落後時列出差異，詢問是否順便升級（碰到才升級）。
5. **新工具**：依 [新工具建立流程.md](../docs/00_公共規格/新工具建立流程.md) 第 7 節進行。
6. **拆解任務**：將本次目標拆成可驗證的小步驟，經使用者確認後開始。

### 「收工」
1. **完工檢查**：對照 [新工具建立流程.md](../docs/00_公共規格/新工具建立流程.md) 第 8 節，列出本次相關項目的結果（未完成的要說明）。
2. **撰寫開發日誌**（含 Handoff 狀態條言），並依 [知識庫連結規範.md](../docs/00_公共規格/知識庫連結規範.md) 填寫開頭四面向欄位；需要新概念時建立概念筆記並登錄至知識庫首頁。
3. **同步文件**：README 工具清單、工具包。
4. **回報新概念**：列出本次新增的概念（名稱 + 面向 + 一句定義），請使用者確認。
5. **產出提交訊息**：依下方「Git 提交訊息格式」產出可直接貼上的 Summary 與 Description，並**明確標出要在哪個 repo 提交**（若同時改到工具與工坊規範，分別產出兩份）。
   - 一般情況直接提交到該 repo 的 `main`。
   - 🌐 GitHub 工具的程式碼變更：走 `feature/功能名` 分支，push 後建立 PR。
6. **依發佈標籤收尾**：📤 詢問是否同步雲端硬碟；🌐 提醒 push。
7. **不執行** `git commit` / `git push`，由使用者手動完成。

### 「讓我看看」
- 依該工具 README 的「使用方式」啟動並說明如何操作。
- 桌面工具：先執行 `build.bat`（若原始碼有變更），再啟動執行檔。
- 工具若有自己的 `.agents/AGENTS.md` 定義「讓我看看」，依該檔執行。

### 「確認狀況」
1. **安全凍結**：本輪不修改任何檔案、不執行有變更性的指令；列出仍在執行的背景任務。
2. **彙整狀態**：目前任務進度、本機已修改的檔案與變更摘要、接下來預計會改什麼。
3. 等待使用者指示，不主動恢復開發。

### 「記想法」
- **觸發不限句型**：使用者說「記下來」「這是個想法」，或描述一個點子但沒有要求馬上實作時（可能是語音輸入，說法每次不同、可能有錯字），一律視為記想法。
- **寫進** [想法收件匣](../docs/想法收件匣.md)：依日期分段，每則寫標題、狀態（💡 靈感）、一句話整理的想法、關聯（相關工具、現有資源）；保留使用者原意，不擴寫成計畫。
- **不動手**：記想法只寫收件匣，不建立工具資料夾、不寫程式；決定要做時再依 [新工具建立流程.md](../docs/00_公共規格/新工具建立流程.md) 轉成工具，並把收件匣狀態改為「→ 已轉成 NN_工具」。
- **找回來**：「開工」第 3 步會帶出相關想法；使用者也可以直接問「有哪些想法跟 X 有關」。

### 「精簡模式」/「詳細模式」
- **精簡模式**：去除客套與贅字，只輸出關鍵技術內容、變更與檔案連結。
- **詳細模式**：恢復完整背景說明與步驟拆解。

### 「自我修復」
當使用者下達指令，或發現規則矛盾、引用失效時：
1. 條列「原本設計意圖 / 實際矛盾 / 根因」。
2. 修正本檔對應條文，並清除過時或廢棄的規則。
3. 同步修正受影響的規範文件，回報改了哪些條文。

### 「整網」
依 [知識庫連結規範.md](../docs/00_公共規格/知識庫連結規範.md) 第 6 節整理開發網：列出可合併的重複概念、久未使用的概念、熱點概念與建議。**只列清單與建議，經使用者確認後才合併 / 刪除。**

### 工具專用指令
- 個別工具的專用指令寫在該工具的 `.agents/AGENTS.md`；使用者說出未定義在本檔的指令時，先到對應工具的規則中查找。

## 5. Git 提交訊息格式

```
<type>(<scope>): <中文摘要>

- 變更重點 1
- 變更重點 2
```

- **type**：`feat` 新功能、`fix` 修正、`refactor` 重構、`docs` 文件、`chore` 雜項 / 建置。
- **scope**：工具的英文代號（如 `desktop-switch`），工坊整體規範用 `workshop`。

## 6. Obsidian 連結規範

Obsidian Vault 開在工坊根目錄。

1. **概念連結**（`[[概念名稱]]`）：只能連到 `docs/知識庫/` 中已存在的概念筆記；沒有合適的就依 [知識庫連結規範.md](../docs/00_公共規格/知識庫連結規範.md) 新建，不留下指向不存在筆記的連結。
2. **文件連結**（連到規範、README 等具體檔案）：使用標準 Markdown 相對路徑並含 `.md` 副檔名（`[標籤](../path.md)`），確保 GitHub 與 Obsidian 皆可用。
3. 路徑大小寫必須與檔案系統完全一致。
