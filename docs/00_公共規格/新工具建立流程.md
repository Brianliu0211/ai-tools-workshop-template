# 🧰 新工具建立流程與工坊管理規範

本文件是 本工坊的**管理 SSOT**：定義工具標籤、版本控制、命名、README 標準與完工檢查清單。
桌面工具的 UI / IPC 技術標準見 [小工具設計與互動規範.md](小工具設計與互動規範.md)。

> **設計原則**：工具都是依個人需求「走一步算一步」長出來的，規範只管必要的一致性，不為未來過度設計。

---

## 1. 兩層分工

| | 🏠 工坊層（工坊根目錄） | 🔧 工具層（`NN_工具/`） |
| :--- | :--- | :--- |
| **管什麼** | 「怎麼做事」：AI 規則、快捷指令、日誌格式、共用設計標準、工具清單 | 「這個東西是什麼」：使用方式、建置、檔案說明、工具特有的設計決定 |
| **檔案** | `.agents/AGENTS.md`、`docs/00_公共規格/` | `README.md`、`docs/`、`.agents/AGENTS.md`（後兩者需要時才建） |

**鐵律**：工具層只寫**自己特有的**內容，不複製工坊規則，需要時用連結引用。所有工具都遵守同一套工坊規則。

**工具專屬 AI 規則**（`NN_工具/.agents/AGENTS.md`）只在工具有專用指令或專屬檢查項目時才建立，開頭必須寫明「先讀工坊共用規則」。

## 2. 工具的兩個標籤

### ① 狀態

| 標籤 | 意義 |
| :--- | :--- |
| 💭 構想中 | 只有想法還沒動工；README 須記錄**構想**與**待釐清問題**，工具清單兼當點子清單 |
| 🟡 開發中 | 正在做 |
| 🟢 可用 | 日常在用（有瑕疵沒關係，有問題再修） |
| 🟠 暫停 | 卡關先擱著；工具 README 須記錄**卡在哪裡**，方便日後接手 |
| ⚪ 停用 | 不再使用；資料夾移至 `_archive/`，編號保留不重用 |

### ② 發佈

| 標籤 | 送出的內容 | 適用情境 |
| :--- | :--- | :--- |
| 🌐 GitHub | 原始碼（push 到 GitHub，供部署） | 需要變成網頁 / 上雲端的工具 |
| 📤 雲端硬碟 | 執行檔 + `README.md`（拿到就能用） | 想分享給別人的桌面工具 |
| 💻 僅本機 | 不送出 | 暫停中，或只有自己用 |

兩個標籤互相獨立，記錄在根目錄 [README.md](../../README.md) 的工具清單。發佈方式改變時只需改標籤，不需改規範。

## 3. 版本控制（git）

> git 管「歷史」，發佈管「送給誰」，兩件事分開。

- **每個工具一個獨立 repo**：工具資料夾內各自 `git init`，存檔歷史只跟著這個工具。
- **工坊 repo**：工坊根目錄 本身也是 repo，但**只存規則與文件**，所有 `NN_*` 工具資料夾都被 `.gitignore` 排除。
- **只有 🌐 GitHub 工具才 push**；其他工具的 repo 只留在本機，不會公開任何東西。日後要上 GitHub，在 GitHub Desktop 按「Publish repository」（或用 git 指令 push）即可，歷史完整保留。
- **不進 git**：`exe` 等編譯產物（由 `build.bat` 重建）、`__pycache__` / `node_modules` / `.next` 等快取、執行期產生的個人設定、`.env*` 機密。
- **提交**由使用者手動完成（例如用 GitHub Desktop），AI 只產出提交訊息。

## 4. 命名與目錄

- **資料夾**：`NN_工具中文名`，兩位數流水號，不重用停用工具的編號。
- **執行檔**：以工具中文名命名（如 `螢幕切換.exe`），不額外複製英文檔名的備份 exe。
- **最低必備檔案**：

```
NN_工具名/
├── .git/ .gitignore   ← 工具自己的 repo
├── README.md          ← 必備，依下方範本
├── <原始碼>            ← .cs / .py / src/ …
├── build.bat          ← 需編譯的工具必備
└── 啟動*.bat / *.exe  ← 使用者實際點擊的入口
```

- **工具開發日誌**預設放在工具內 `docs/開發日誌/YYYY-MM/`（格式見 [開發日誌規範.md](../03_開發日誌/開發日誌規範.md)），跟著工具自己的 git 歷史走。已有既定位置的工具沿用原位置，並在工具 `.agents/AGENTS.md` 註明。

## 5. 工具 README 範本

```markdown
# 工具名稱

一句話說明這個工具解決什麼問題。

> 符合規範：新工具建立流程 vX、小工具設計與互動規範 vX（桌面工具才需要）

## 🚀 使用方式
怎麼啟動、怎麼操作（雙擊什麼、右鍵選單有什麼）。

## ⚙️ 需求環境
作業系統、執行環境、需要的金鑰或環境變數「名稱」（不寫實際值）。

## 🔨 建置方式
如何從原始碼產生執行檔（例如：雙擊 build.bat）；無需建置則寫「免建置」。

## 📂 檔案說明
每個檔案的用途。

## ⚠️ 注意事項
會修改哪些系統設定、如何還原、已知瑕疵與限制。

## ⏸️ 暫停紀錄（狀態為 🟠 暫停時才需要）
卡在哪裡、試過什麼、下次可以從哪裡切入。

## 💭 構想（狀態為 💭 構想中時才需要；開工後可保留作為原始需求）
想要的功能、使用情境、待釐清問題。
```

> 💭 構想中的工具，「使用方式 / 需求環境 / 建置方式 / 檔案說明」可先寫「尚未開始」。

## 6. 規範改版與「碰到才升級」

1. 每份公共規範最下方維護「📜 變更紀錄」：版本、日期、改了什麼、哪些工具需跟進。
2. 工具 README 的「符合規範」記錄該工具對齊到哪一版。
3. **碰到才升級**：規範改版不強迫所有工具立刻跟進。下次「開工」處理某工具時，AI 比對版本，落後就提醒使用者是否順便升級。

## 7. 新工具建立流程

1. **確認用途**：與使用者確認要解決什麼問題、技術選型、預計的發佈方式。
2. **建立目錄**：取下一個流水號建立 `NN_工具名/`，執行 `git init`，放入 `.gitignore` 與 README 範本。
3. **登記清單**：在根目錄 README 工具清單新增一列（🟡 開發中），並在 `docs/知識庫/工具/` 建立該工具的概念筆記、登錄至[知識庫首頁](../知識庫/知識庫首頁.md)。
4. **開發**：桌面工具須遵循 [小工具設計與互動規範.md](小工具設計與互動規範.md)；新增 SDK / 套件時同步更新 [工具包.md](../工具包.md)。
5. **完工**：逐項通過下方清單。

- [ ] 根目錄 README 工具清單的狀態與發佈標籤已更新

  - 📤 雲端硬碟 → 主動詢問：「這個工具已完工測試通過，請問要同步一份最新版本（執行檔 + README）至雲端硬碟嗎？」
